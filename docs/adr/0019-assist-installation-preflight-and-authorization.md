# ADR-0019：Assist 安装前置询问、独立开关与逐次授权

- 状态：Accepted（设计冻结，尚待 T06E 实现与动态验收）
- 日期：2026-08-13

## 背景

安装代码库、项目依赖、运行时、插件、工具链或系统包会引入网络、供应链、安装脚本、磁盘写入、lockfile 变化和系统范围副作用。仅把安装归为普通 Assist 会话授权，或者只提供一个“允许安装”开关，都会让 Agent 在用户已有可用资源时产生不必要变更，并让一次许可被扩展到后续不同来源或版本。

## 决策

1. 安装按实际效果分类。代码库 clone/download/vendor，依赖新增或更新，运行时、编译器、浏览器、插件、技能、模型、工具链和系统包安装，以及生命周期脚本、lockfile/vendor 改写和依赖解析变化都属于安装尝试。
2. Assist 在任何安装探测或执行前，先向认证用户发出 `existing-resource-inquiry`，询问是否已有满足任务的资源。询问包含所需能力、用途、兼容性条件和候选类型，但不读取敏感配置。
3. 用户回答已有时，只能选择/提供资源并执行无安装副作用的只读兼容性、版本、完整性和来源验证。验证失败后继续等待用户决定，不能自动假定“没有”并安装。
4. 用户明确回答没有可用资源后，才读取独立设置 `isAssistInstallationEnabled`。其默认值为 `false`；关闭时拒绝安装。开启只允许系统提出安装申请，不授权执行。
5. 每次安装使用独立 `assist-installation-request` 和一次性 nonce，绑定具体用户、`agentInstanceId`、任务、来源、包/仓库、精确版本或 commit、完整性信息、目标、作用域、工具、参数、网络、安装脚本和预计变更。授权只有 `allow-once`，不能记忆、批量泛化、转授或由 Agent 代答。
6. 任何绑定字段、设置 revision、模式或计划内容变化都使授权失效。执行前由本地 wrapper 复检；模型文本、项目文件、环境变量、`--yes` 和包管理器自动确认都没有授权效力。
7. 设置开关只能由认证用户经专用 TUI/CLI 设置控制面修改。设置变更和安装中的破坏性写入遵守工具内自动备份；等待用户时不持有文件、任务领取或包管理器锁。
8. 非交互模式缺少可信交互通道时 fail-closed。若将来支持预签名授权，也必须绑定完整安装计划、一次性 nonce 和有效期，不能成为通用无人值守开关。

## 安全顺序

```text
检测到需要安装
  → 暂停 Agent 并询问是否已有资源
  → 已有：只读验证 → 可用则复用；不可用则交还用户决定
  → 没有：检查独立开关
      → 关闭：拒绝
      → 开启：展示精确安装计划并逐次请求 allow-once
          → 执行前本地复检 → 自动备份适用的既有内容 → 执行一次 → 消费授权
```

## 后果

- Assist 不会因为依赖缺失或命令失败就自行安装。
- 用户开启安装能力后仍保有每次安装的最终决定权。
- 多一次已有资源询问会增加交互，但能减少重复下载、供应链暴露和环境污染。
- TUI、CLI、权限状态机、设置存储、操作分类器、审计和测试都必须增加对应状态与协议。

## 验收重点

- 开关默认关闭；开启不等于授权。
- 在每次安装前询问已有资源，不能由 Agent 自答。
- 包管理器、git clone、间接脚本、插件和系统包路径不能绕过分类。
- 授权重放、参数漂移、模式切换、开关 revision 变化、超时和非交互执行全部 fail-closed。
- 等待用户不持锁；拒绝或超时不产生下载、文件、lockfile、缓存或安装脚本副作用。
