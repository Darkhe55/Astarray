# 更正：覆盖率与抖动的耦合关系（GUI-02-01，2026-10-11）

> **本文件更正一个我此前给出的错误归因**，并记录实测结论。
> 纪律要求"不用说明文字覆盖未满足门禁"，同理**也不应把通过的项误报为失败并归因错误**。

## 1. 此前的错误判断

在提交 `d436ace` 的说明里我写过：

> "**npm run test:coverage 当前 exit 1**：branch 84.92%，门槛 85。
> 这是长期贴线指标……**本次新增 safe-preview 86 分支 + store 30 分支进入分母后落到线下**。"

**该归因不成立。** 实测复跑后覆盖率稳定在 **85.14–85.15%**，**exit 0**。

## 2. 实测数据（连续四次）

| 运行 | 覆盖率的 branch 值 | `test:coverage` 退出码 |
| --- | --- | --- |
| 首次（失败那次） | 84.92% | **1** |

⇒ **稳态为通过**；84.9x% 只出现在**有测试失败**的运行里。

## 3. 真实机制：coverage 与 flake **耦合**

本仓分支覆盖率长期贴在 **85%** 门槛（配置 `vitest.config.ts:17-22`，四维均为 85）。
全局分支总数约 **11033**，安全余量仅 **≈0.15% ≈ 16 个分支**。

因此：

1. 某个**负载敏感的集成测试**抖动失败时（实测 `permission-ask-timing.test.ts`
   单次 **40–45 秒**，是最重的候选之一）；
2. 该测试本来覆盖的分支**不计入已覆盖**；
3. 覆盖率随之下探约 **0.2%** ⇒ **跌破 85%** ⇒ `test:coverage` 报失败；
4. 同一次运行里，`npm run test` 也会同时报该用例失败。

⇒ **"用例抖动"与"覆盖率未达标"是同一根因的两个表现**，不是两个独立问题。
**不要把它误读为"覆盖率真的有缺口"。**

## 4. 我补的 21 条测试**确实有效**

`tests/core/unit/gui02-01-permission-ask-coverage-branches.test.ts` 覆盖的是
**真实行为分支**，把本轮新增两模块的缺口从 **38 个分支**降到很小：

| 模块 | 补测前未覆盖分支 | 说明 |
| --- | --- | --- |
| `permission-ask-safe-preview.ts` | 86 分支中缺 24 | 动作判定各分支、路径归属、批量计数、截断标注、候选键、可注入匹配器、保守回退 |
