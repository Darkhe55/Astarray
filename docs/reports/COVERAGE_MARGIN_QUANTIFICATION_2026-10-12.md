# 覆盖率贴线的成因、修复与稳定性实测（2026-10-12）

> 背景：`test:coverage` 的**分支**全局门槛为 **85**，本会话多次观测到它在门槛附近摆动
> （84.86 / 84.97 / 84.99 / 85.00 / 85.01 / 85.02 / 85.03），并**两次**因此让门禁翻红。
> 本文件固化**量化结论**与**修复动作**，供后续会话判断"何时该补、何时不该补"。

## 1. 量化事实（实测，非估计）

| 量 | 数值 | 来源 |
| --- | --- | --- |
| 全局分支总数 | **11178** | `coverage/coverage-summary.json` |
| 距离 85% 的 1 个分支 | ≈ **0.009 个百分点** | 1 ÷ 11178 |
| **单条测试**的典型贡献 | ≈ **0.01 点**（多为 1 个分支） | 补两条后 84.97 → 84.99 |
| **观测到的抖动量级** | ≈ **±0.02 点** | 同一代码不同运行：84.97–85.03 |

**⇒ 关键推论**：**抖动量级 > 单条测试贡献** ⇒ **零散补分支无法可靠越过门槛**。
本会话曾连续补入 4 条边界测试仍停在 84.99，即为此推论的经验证据。

## 2. 成因（两类，须分开看）

1. **真实缺口**：加入新代码（GUI-02 的权限询问/安装专用流程）后分支总数上升，
   而新代码分支**未同步测试** ⇒ 覆盖率**真实下降**（85.02 → 84.86）。
   **这是必须补的**。
2. **负载敏感测试抖动**：某些集成测试在负载下偶发失败 ⇒ **其覆盖的分支不计入** ⇒
   覆盖率瞬时下探（约 −0.2 点）。**这不是真实缺口**。
   详见 `COVERAGE_FLAKE_COUPLING_CORRECTION_2026-10-11.md`。

**判别方法**：若 `npm run test` 同时出现 **1 个 failed**，则是抖动；
若全绿而覆盖率仍不足，则是**真实缺口**。

## 3. 本会话采取的修复（结构性，非零散）

- **目标选得准**：`packages/tui/src/cli/commands.ts` 的**未覆盖分支最多**
  （缺 297/899 ≈ 全局 **2.7%**），且其命令**此前仅由子进程驱动**（v8 不可见 ⇒
  长期低覆盖，B6R-10 已记录该成因）。
- **办法**：直接**进程内**调用命令函数（不 spawn），使覆盖可见。
  新增 `tests/tui/unit/gui02-commands-profile-coverage.test.ts`（4 条，面板命令全生命周期）。
- **效果**：全局分支 **84.99 → 85.01**；`test:coverage` 由 **exit 1 翻正为 exit 0**。

## 4. 稳定性实测（2026-10-12，连续 3 次）

| 运行 | 退出码 | 分支 |
| --- | --- | --- |
| 第 1 次 | **0** | 85.00 |
| 第 2 次 | **0** | 85.03 |
| 第 3 次 | **0** | 85.00 |

⇒ **当前在负载下可连续通过**，但**余量仅 0.00–0.03 点** —— **仍贴着门槛**。

## 5. 结论与建议（不擅自改门槛）

- **不要**为零散分支写测试（性价比极低，且会被抖动吃掉）。
- 若要取得**远离抖动带**的余量（建议目标 **≥85.3**，约需再覆盖 **35+ 个分支**），
  应继续对 `commands.ts` 等**大缺口文件**做结构性补测：
  优先覆盖**仅由子进程驱动**的命令（v8 不可见是主要成因）。
- **备选（属用户决策，本会话未擅自实施）**：
  ① 调整 85 门槛；② 串行化负载敏感测试以消除抖动；
  二者都会改变门禁语义或测试策略，**应由用户决定**。
