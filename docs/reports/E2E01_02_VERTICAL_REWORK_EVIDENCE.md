## 1. 本切片覆盖的纵向步骤

每一步都走**产品入口**（`AstarrayApplicationFacade` + Provider 运行时 + 真实工具循环 +
完成门禁），step 之间的编排由本验收流程负责：

| 步骤 | 产品执行 | 证据 |
| --- | --- | --- |
| ① 实现（第一版，故意写错） | devolve 模式下 provider worker 经 `replaceFileContent` 真实覆盖 fixture 实现文件 | 任务 done；文件内容为错误实现 |
| ② 测试（冻结断言） | 以 fixture 的冻结预期判定 | 第一版摘要 ≠ 冻结预期 → **触发返修** |
| ③ 返修（第二版） | 重新走产品入口写入参考实现 | 任务 done；文件为正确实现 |
| ④ 测试通过 + 产出产物 | 写出 `out/summary.json` 与 `out/test-evidence.json` | 摘要与冻结预期一致；**sha256 = `fc1328fb…5830d`，与 E2E-01-01 证据完全一致** |
| ⑤ 独立验收 | 第三个产品 mission（assist 只读）经 `readFile` 复核产物 | Provider 收到产物正文（含"已完成 2/4"），任务 done |
| ⑥ 身份分离 | 三个 mission 各自的 worker 身份 | 从 `missions/<id>/agents/` 取证：3 个互不相同的 `agentInstanceId` |

## 2. 关键观察

- 完成门禁（切片 3）只保证"写操作未失败"，**不判定写的内容是否正确**：第一版错误实现同样以
  `done` 收口——这正是"必须由独立测试与独立验收判定"的实证。
- 返修走的是与首次实现完全相同的产品入口（新的 mission、新的 worker 身份），不存在"就地改状态"。
