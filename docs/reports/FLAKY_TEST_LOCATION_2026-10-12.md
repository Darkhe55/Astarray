# 负载敏感抖动：定位结果（2026-10-12，8 次全量实测）

> 上一轮报告（`TEST_ENVIRONMENT_DIFFERENCES_AND_FLAKINESS_2026-10-12.md`）把"未定位抖动源"
> 列为未完成项。本轮**专门做了定位**，结果如下。

## 1. 方法

连续 `npm run test` **8 次**，每次**完整输出落盘**（`.tmp/flake-logs/run-N.log`，`/tmp` 级临时目录），
再比对失败轮的测试名与断言。

## 2. 实测结果

| 运行 | 退出码 | 结果 |
| --- | --- | --- |
| 1 | 0 | 3019 passed |
| 2 | **1** | **1 failed** — `tests/core/integration/anthropic-messages-runtime.test.ts:413` |
| 3 | 0 | 3019 passed |
| 4 | 0 | 3019 passed |
| 5 | **1** | **1 failed** — `tests/core/integration/completion-gate-counterexamples.test.ts:351` |
| 6 | 0 | 3019 passed |
| 7 | **1** | **1 failed** — `tests/core/integration/reliability-r4-ledger-concurrency.test.ts:172` |
| 8 | 0 | 3019 passed |

**抖动率：3/8 = 37.5%**（每次全量运行约 1/3 概率出现 1 个失败）。

## 3. 关键结论

**三个失败点各不相同** ⇒ 这**不是**"某个测试写得差"，而是**框架级的负载敏感**：

| 文件 | 失败用例 | 耗时特征 |
| --- | --- | --- |
| `anthropic-messages-runtime.test.ts` | （第 413 行附近） | 221ms（该文件整体）|
| `completion-gate-counterexamples.test.ts` | **B. 未解决的写失败后声称完成 → 必须被拦** | 129ms |
| `reliability-r4-ledger-concurrency.test.ts` | **④ 多轮交错并发（4 轮 × 6 会话）** | **6235ms** |

**均为真实断言失败，不是超时**（无 `Test timed out`）。
其中 `reliability-r4-ledger-concurrency` ④ 与本会话既有记录一致（长期已知负载敏感）；
另两个为**本轮新定位**。

## 4. 影响（为何值得优先处理）

1. **门禁可信度**：约 1/3 的运行会红，而**每次红的测试不同** ⇒ 开发者容易养成"复跑就好"的习惯，
   从而**掩盖真实回归**（本会话已发生：我一度以为某次红是抖动）。
2. **污染覆盖率门禁**：抖动失败时该测试覆盖的分支**不计入** ⇒
   `test:coverage` 的**分支**指标瞬时下探约 0.2 点并**跟着翻红**
   （当前分支 85.05，距门槛 85 仅 0.05）⇒ 两个门禁**同时**不可信。

## 5. 候选处理方案（**均未实施**，属用户决策）

| 方案 | 说明 | 代价 |
| --- | --- | --- |
| **A. 提高余量** | 继续补覆盖率到 ≥85.3，让覆盖率门禁不再被 0.2 点抖动打穿 | 需再覆盖 30+ 分支；**不解决测试失败本身** |
| **B. 串行/隔离** | 对上述 3 个文件设 `sequence.concurrent = false` 或独立跑 | 拖慢全量；需确认 v8 覆盖仍可见 |
| **C. 定位竞态并修产品** | 三个失败疑似共享"并发/时序"成因，值得逐个查清 | **最贵、最有价值**；需要可复现的最小场景 |

**我的建议**：**C → B → A**。理由：抖动是**真实的不确定性**；若其中含产品竞态，
改测试策略只会掩盖它。但 C 需要**先能稳定复现**（当前 37.5% 概率），
故建议先做 **B 的隔离复现**（单独反复跑这 3 个文件）以取得稳定复现，
再决定是否修产品。
