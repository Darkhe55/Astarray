## 1. 缺陷陈述（可核对）

用户 2026-10-11 的公共授权契约要求（原文）：

> 请求绑定具体操作、**完整参数指纹**及权限 revision；**过期、撤销、参数变化均不能复用批准**。

**现状**：`shouldReusePreviousApproval`
（`packages/core/src/orchestration/permission-ask-contract.ts`）**只比较
工具名 + 目标路径**：

| 比较项 | 是否参与判定 | 证据 |
| --- | --- | --- |
| `toolName` | ✅ | `:93` |
| **目标路径**（`path`/`filePath`/`targetPath`/`directoryPath`） | ✅ | `:54,96,97,101` |
| **其余全部参数** | ❌ **完全不参与** | 判定读区内无其它 `argumentsJson` 比对 |
| `hasSucceededWithSameTarget` | ✅（fail-closed 用） | `:104` |

**后果**：**同一目标路径、内容不同**的两次写入被判定为 `reuse-without-asking`
⇒ **参数已变化却复用了批准**，与 S3 直接冲突。

**已固定为可核对反例**：`tests/core/unit/gui02-01-permission-ask-fingerprint-gap.test.ts`
用例 ①（当前为绿，因为断言的是**现状**；文件头已明确声明
"**不是缺陷已修的证明**，而是把差距固定下来供返修改写"）。

## 2. 为什么不能"顺手改成比完整参数"

现有复用语义是 **2026-10-02 用户明确选择的"方案 B"**：
> 同一授权周期内**容忍"无副作用重试"的参数抖动**（参数只有换行/键序等格式差异）。

- 直接改成比较完整 `argumentsJson` ⇒ **取消该容忍**（行为变更），
  会让"仅键序不同"的重试重新弹询问，**与方案 B 的既有决策冲突**；
- 正确做法是**规范化后比对**（键序无关），并在判定中同时纳入
  **有效期**与**请求 revision** —— 后者需要先有"请求实体"（见 §4）。

## 5. 前置：permission-ask 缺"请求实体"

S3 的"过期、撤销、参数变化不得复用"与 N3（过期裁决被拒）都需要
**请求自身的状态与生命周期**，而当前公开契约**没有**：

| 缺失 | 说明 |
| --- | --- |
| `askIdentifier` | 请求身份（多页面同步、拒绝陈旧裁决的锚点） |
| 请求**状态**（pending / allowed / denied / expired / revoked） | 状态迁移的载体 |
| 请求自身 **revision** | 拒绝陈旧裁决 |
| **有效期** | 过期判定 |

> **注意（避免误引用）**：全仓搜到的 `askIdentifier`（380 处）、
> `operationFingerprint`（64 处）、`expiresAtIso`（72 处）属于
> **安装授权**、**跨项目授权**等**其它子系统**，**不是** permission-ask 的。
> 本条目已核实这一点（见 `tests/core/unit/gui02-01-permission-ask-fingerprint-gap.test.ts`
> 的 N3 前提用例：公开契约字段仅 4 个）。
