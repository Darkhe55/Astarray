### 2.2 ⚠️ 「授权和追认无内容」—— **经核实是 mock 的必然结果，不是缺陷**

我**从服务端**核对了当时的事实（不是靠推测）：

```
GET /permission-asks → {"entries":[]}
GET /verifications   → {"entries":[]}
```

⇒ mock 运行时**不产生**权限询问与待追认项 ⇒ 两个区块为空。
**⚠️ 边界**：真实 Provider + 需要授权的工具场景下这两区才应有内容，
**该场景本轮未验**（需真实凭据，遵从本会话纪律未启用）。

### 2.3 ⚠️ 「所有项目显示暂不可恢复」—— **用户少看到 1 个可恢复项，我核出了它**

我从 `/recovery` 逐条核对了全部 **103** 条：

| 结果 | 条数 |
| --- | --- |
| 「无可信检查点 ⇒ 禁用」 | **102** |
| **可恢复（`hasTrustedCheckpoint=true`、未损坏、无活跃租约）** | **1** —— `mission-e1f86464` |

⇒ 用户第一次"没看到可用的"是**真实可理解的**：**102:1**，且它按字典序埋在
`mission-e0…`／`mission-e1…` 那一段里（我据服务端数据定位后请用户按 `Ctrl+F` 搜索，

**这是可用性（时延）问题，不是状态判定错误** —— 禁用原因显示是正确的。

## 3. ⭐ 本轮最有价值的一条：**恢复全链路端到端走通（真实用户点击）**

用户点击 `mission-e1f86464` 的恢复按钮后，界面显示：

```
未恢复（recovery-blocked-by-core）：
mission-status-done: mission 已处于终态（done/cancelled），禁止重复执行；
阻塞项：mission-status-done
```

**该理由来自产品核心**，我核对过源码出处：
`packages/core/src/orchestration/recovery-center-controller.ts:278`
（`item: mission-status-${...}`、`decision: "mission-already-terminal"`、
`reason: "mission 已处于终态（done/cancelled），禁止重复执行"`）。

⇒ 这一下同时证实了四件事（此前只有源码级/HTTP 级证据，**没有人真的点过**）：

1. 恢复按钮的**可用态**确实按条件计算（这条没被禁用）；
2. **`POST /commands/recovery-resume` 真实往返成功**（显式确认 → 服务端 → 核心）；
3. **服务端拒绝理由能被用户看懂**（含 `outcome` 与 `blockingDecisions`）；
4. 核心**如实拒绝**了"对终态 mission 重复执行"，**没有被美化成"已恢复"**。

## 4. ⚠️ 我在核对时发现的**真实缺口**（我的问题，非用户操作）

**恢复中心 `/recovery` 一次性返回 103 个 mission（无分页）。**

卡片 `GUI02_..._TASK_CARD.md` L60/L77 写着：

> **分页、按需加载**：不得一次读取全部 97 个 mission。
> （GUI-02-03）… 分页按需加载（不得全量读 97 mission）

**范围说明（我不夸大）**：该条的**明文语境是"历史任务视图"**，而用户在历史区确实得到了分页。
但**恢复中心**目前是全量返回，**在 103 条规模下直接损害可用性**
（可恢复项 102:1 被淹没 —— 这正是用户实际遇到的）。
⇒ 我把它记为**待修**，**并先征询用户是否动代码**，而不是自行扩大改动。
