# 已知问题：读写格式测试依赖工作区行尾（2026-10-12 发现）

> 发现方式：暂停期间做 **HEAD 级验证**（用独立 `git worktree` 检出 `HEAD` 后跑门禁），
> 与「在工作区跑门禁」的结果**不一致** —— 这正是我此前长期缺失的验证方式。

## 1. 现象（可复现）

| 环境 | `tests/core/unit/read-format-other-languages.test.ts` | `npm run test` |
| --- | --- | --- |
| **当前工作区** | **11/11 通过** | （我此前各轮均为绿） |
| **干净 HEAD 检出**（独立 worktree） | **1 failed** | **1 failed \| 3015 passed** |

失败用例：`READ-FORMAT-04b Shell > # 注释省略；heredoc 与引号内容保留；静态 source 省略、动态 source 保留标注`

失败断言：

```
expected '\n\n\r\nsource ./lib/common.sh\r\n. .…' not to contain 'source ./lib/common.sh'
```

## 2. 根因（已定位，非推测）

| 事实 | 值 |
| --- | --- |
| `core.autocrlf` | **`true`** |
| 仓库 `.gitattributes` | **不存在** |
| 工作区的 `tests/fixtures/read-format/config/sample.sh` | **LF** |
| **干净检出**的同名文件 | **CRLF**（被 `autocrlf` 在检出时转换） |
| `git check-attr text eol -- <该文件>` | `unspecified` / `unspecified` |

⇒ 该测试对**工作区行尾**敏感：把 `source ./lib/common.sh` 判为**静态 source 应省略**，
而 CRLF 使该判断不成立 ⇒ 文本仍含该行 ⇒ 断言失败。

## 3. 影响范围与性质

- **影响**：**新克隆 / 干净检出 / CI**（凡 `core.autocrlf=true` 且无 `.gitattributes` 的环境）
  会在该文件上失败。我这台机器的工作区因历史检出（行尾为 LF）而**长期掩盖**了它。
- **性质**：**不是**本次会话引入（今天的改动都在 GUI 授权与安装专用流程路径，与该测试无关）；
  已在 `d332ded`（补交 async 修复）**之前**的 `e88ed15` 上复现 ⇒ 属**既有问题**。
- **为何长期未被发现**：所有轮次的门禁都在**同一个工作区**里跑，
  而工作区行尾与"干净检出"不同 ⇒ **门禁结果无法代表干净检出的结果**。

## 4. 建议的最小修复（未实施，理由见下）

**方案 A（推荐，非侵入）**：添加 `.gitattributes` 固定夹具为 LF：

```
tests/fixtures/** text eol=lf
```

理由：测试夹具属**内容敏感**资产，其字节必须**确定**；固定 LF 即可让所有平台一致。

**方案 B**：让该测试在断言前**归一化行尾**（`\r\n` → `\n`）后再判定。

**我本轮未实施的原因（如实）**：
- 方案 A 会**改变全仓检出行为**，对已在本机以 CRLF 检出的文件会引入大面积差异；
- 方案 B 触及**产品判定语义**（"静态 source 是否省略"）附近的测试，需先读清该判定是否
  **本就应当**对行尾不敏感，再决定在测试侧还是产品侧修；
- 我这一轮上下文已接近上限，**不适合**做这种需要完整回归的改动。

**故本轮只记录，不改。**

## 5. 由此得出的流程教训（重要）

**「工作区跑门禁绿」不等于「HEAD / 干净检出绿」。**
本会话已多次出现同类问题：
- 覆盖率抖动的判别；
- 我遗漏提交一个文件导致 `origin/main` `typecheck` 失败（见 `d332ded`）；
- 本问题：工作区行尾掩盖了测试对行尾的依赖。

⇒ **建议把「HEAD 级验证」纳入收尾流程**（例如用 `git worktree` 检出 `HEAD` 后再跑一次门禁），
而不是只依赖工作区结果。
