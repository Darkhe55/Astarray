# OBS-01／PERF-01-01：**性能观测开销测量**（2026-11-08）

- **由来**：`PLAN_STATUS` 的 OBS 行经第 81–83 轮对账后，**唯一未覆盖项**就是本检查点里的
  「**用同一工作负载测开关前后 CPU/内存/延迟，记录设备与样本**」。
  卡内第 89 行明写「观察开销预算**先测再定**，不预填性能提升或费用节省百分比」
  ⇒ 不测就**给不出开销预算**。第 83 轮把 `perfSampleSink` 接进生产装配并加了
  `isPerformanceCollectionEnabled` 开关（**缺省关**）后，本测量才**成为可能**。
- **本报告是实测记录，不是承诺**；口径、设备、原始样本、未测项全部列出。

## 1. 冻结的测量口径（可复跑）

被测代码 = **构建产物**（`dist/public-sdk.js` 导出的 `PerfEventStore`），脚本：
`scripts/measure-perf-collection-overhead.mjs`（运行 `node scripts/measure-perf-collection-overhead.mjs`，**exit 0**）。

| 项 | 冻结值 |
| --- | --- |
| 工作负载 | **单次"工具执行后上报一个样本"**；与生产一致：sink **在关键路径上被 `await`** |
| 关（基线） | 生产中开关关时**根本不调用 sink** ⇒ 基线为等价空转循环 |
| 开 | `await PerfEventStore.append(sample)`（**真实 JSONL 落库**） |
| 采样预算 | **2000 样本/轮** |
| 预热 | **200 次/变体** |
| 重复 | **3 轮**，逐轮**交替顺序**（抵消热降频等漂移）；本报告共 **3 次独立整跑** |
| 延迟 | `performance.now()` 包整轮，取**中位数** |
| CPU | `process.cpuUsage()` user+system 增量（µs） |
| 内存 | 轮前/轮后 RSS + **25 ms 轮询峰值**（**非精确峰值**，如实标注） |

## 2. 设备与样本

| 项 | 值 |
| --- | --- |
| 平台 | **win32（Windows 11，内核 10.0.26100）** ← **本机；Linux／macOS 未实测** |
| 架构 | x64 |
| CPU | 13th Gen Intel(R) Core(TM) i7-13700HX，**24 逻辑核** |
| 内存 | 15.7 GB |
| Node | **v24.18.0** |

**三次独立整跑（每次 3 轮 × 2000 样本）**：

| 跑次 | 每次观测 **+墙上时间** | 每次观测 **+CPU** | **落库字节/样本** | 轮询 RSS 增量（2000 样本） |
| --- | --- | --- | --- | --- |
| ① | **274.47 µs** | 226.5 µs | **382.4 B** | +978,944 B |
| ② | **267.21 µs** | 266.0 µs | **382.4 B** | +544,768 B |
| ③ | **263.02 µs** | 242.0 µs | **382.4 B** | +475,136 B |

- **字节数三次完全一致（382.4 B/样本）** —— 该量是确定性的（同一份样本内容）；
- 墙上/CPU 有 **~4% 跑间波动**（263–275 µs / 227–266 µs），属机器噪声，故给区间而非单点；
- RSS 增量波动较大（475–979 KB）⇒ 受 GC 与**内存保留**共同影响，见 §3。

## 3. 结论与可用的口径数字

| 指标 | 实测 |
| --- | --- |
| **单次工具调用的额外延迟** | **≈ 0.26–0.28 ms**（sink 被 `await` ⇒ 直接加在关键路径上） |
| 单次工具调用的额外 CPU | ≈ 0.23–0.27 ms |
| **落库增长** | **382.4 B/样本**（即 1 万次工具调用 ≈ **3.7 MB**） |
| 内存保留上限 | `DEFAULT_MAXIMUM_PENDING_SAMPLE_COUNT = 1000` ⇒ **内存中最多保留 1000 条**（有界），超出即计入 `droppedSampleCount`（**不静默当零**） |

**⇒ 建议的"观察开销预算"（提案，待卡/用户确认）**：
**单次观测新增延迟 ≤ 2 ms、落库 ≤ 1 KB/次、内存保留受 1000 条上限约束**。
理由：实测 ≈0.27 ms ⇒ 该预算留约 **7 倍余量**，既不至于因机器差异误报，
也**不允许**观测膨胀到用户可感知的量级（工具调用本身通常是毫秒级）。

## 4. ⚠️ 未测项（**不报零**，按卡内纪律如实列出）

1. **跨平台（Linux／macOS）未实测** —— 本机是 Windows；卡内第 89 行要求"跨平台未实测明确标未验证"。
   （文件 I/O 性能与文件系统密切相关，**不得**把本机数字外推到其他平台。）
2. **精确峰值内存未测得** —— 只有 25 ms 分辨率的轮询峰值，**不是精确峰值**。
3. **真实 Provider 端到端延迟影响未测** —— 本脚本只测"观测本身"的开销，
   **不假装**测了模型往返（那需要真实凭据与额度）。
4. **单次样本的落库耗时未与磁盘类型分离** —— 未区分页面缓存命中与真实落盘。

## 5. 本轮顺带修掉的一个**我自己的测量 bug**（值得记）

第一版脚本统计落库字节时只扫了 `baseDirectory` **根目录**下的文件，而 store 实际写在
**`<baseDirectory>/perf/samples.jsonl`**（**子目录**）⇒ 第一版输出 **`0 B/样本`**。
那正是本卡明令禁止的「**无法测量不报零**」。
**已修**：改为量真实路径，且**量不到时返回 `null`（不返回 0）**，由报告如实写"未测得"。
修后三轮均为 **382.4 B/样本**（完全一致）。
