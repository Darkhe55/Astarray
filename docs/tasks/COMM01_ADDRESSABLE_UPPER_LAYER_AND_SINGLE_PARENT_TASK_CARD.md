## 2. 最小语义与边界

### 2.1 “全连接”指可寻址，不指全员广播

- 同项目内主层集合 M 与次级集合 S 默认逐对双向可达，即项目内默认全连接的二部图；无需为每一条同项目边单独申请通信授权。不要求主层内部或次级内部自动全连接；身份、任务及会话可见性校验仍逐次执行。
- 单会话仍只有一个当前用户沟通主 Agent。同项目有多个会话主 Agent 时，项目内主/次级也默认可达，但不得共享或自动注入彼此的会话历史。
- 跨项目连接按需申请，必须由目标项目有权主 Agent 或认证用户授权。授权绑定源/目标项目、具体通信对象或明确项目角色范围、消息类型、用途、有效期和 revision，可撤销；限定范围内允许请求与关联回复，不构成两个项目全部 Agent 自动互通，也不可再转授权。本卡不取消 PROJECT-01 隔离，不实现多人协作或秘书功能。
- 项目主 Agent 的批准通过认证会话输出交由本地控制面落地，不新增主模型写工具；本地验证批准者确属目标项目且有权代表该项目，模型自称项目主 Agent 不构成授权。请求方不能自批目标项目授权；主 Agent 不可用时可等待或由用户批准，不自动放行。
- 全连接不赋予所有权：每个次级保留自己的所属项目与任务权威。外来主 Agent 可提出协作/查询；非所属任务发布源的指导由所属控制面检查并转成提案，不得覆盖原任务、提权或改变优先级来源。
- 主模型保持只读工具范围；输出定向提案由本地控制面认证与投递，不为主模型开放副作用发送工具。报告只入具体主 Agent 的报告索引，不自动唤醒模型。
- 通信授权不等于文件访问、复制、安装、Git 或记忆授权。放权模式也必须受通信域和有效作用域约束，不自动开通所有项目。

### 2.1.1 跨项目只读与同层建议（用户补充）

- 跨项目连接始终为只读协作：只在明确授权范围查询状态、读取资料、交换建议与关联回复；读取资料仍遵守 PROJECT-01 的资源授权，不能因通信许可读取整项目或个体记忆。
- 主与主、次级与次级允许按需建立经目标项目有权主 Agent 或用户批准的同层建议通道；不是同层默认全连接，也不改变同项目主—次级默认全连接规则。
- 最低级执行者不新增对外通信安排：三级/四级涉及跨项目同层协作时由唯一直属上级代理转达，保留双方具体来源；执行者仍只认识一个上级。
- 外来 Agent 不得直接修改目标项目文件、配置、任务偏序集、权限、Git 分支或远端；不得通过命令、工具调用、共享目录、转发消息或自动执行建议间接绕过。建议入口只登记建议/消息，不自动转为可执行任务。
- 目标项目有权 Agent 可独立采纳建议，经本地控制面建立该项目的新任务并按本项目权限执行；记录原建议来源、采纳者及任务关联。通信批准不等于执行批准，外来来源不得伪装成用户最高优先级任务。
- 只读限制也适用于放权模式；本卡不提供跨项目写入授权升级。拒绝写入时可说明“请提交建议，由目标项目处理”。

### 2.2 执行层只认唯一直属上级

> **读法提示（2026-10-22 补，源于一次真实误读）**：本节约束的是**执行层的报告/请示方向**
> （三级/四级"只向唯一直属上级请示报告"，其他协作由上级**代理转达**），
> **不是一条普遍的"谁有资格给谁发消息"规则**。
> 上层（主层↔次级层）依 §2.1 是**默认全连接**；**反馈走任务发布者的反向通道**，
> 与上下级关系无关。把本节误读成"通信授权"会**阻断**同项目主↔次级的默认可达
> —— 本会话 2026-10-18～10-20 的交付正是这么错的（详见 §6 订正）。

- 三级固定归属一个次级，四级固定归属一个三级；同一有效关系 revision 下，任务控制、求助、完成与中断报告只通过该上级。三级即使下派四级，自己的上级仍不变。
- 最低级执行者不接收上层全网目录，不选择收件人，不承担转发规划；本地工具提供 `reportToParent` / `requestParentHelp` 等语义，运行时填入唯一目标。
- 兼容旧通信转交规则：涉及三级/四级目标的跨上级句柄改为向其直属上级的协作收件箱递交请求，由上级转达；不允许第二上级直接下令。转达保留原始来源、转达者与任务关联，不冒充直属上级原创。
- 本条明确收窄旧的“可向被转交的下级直接发送 instruction”设计；旧 grant 不静默扩大或延续。迁移时失效旧直达 grant，并返回需重新路由的明确状态。
- 原上级不可用时暂停并存档，不让执行者自行找新上级。控制面在安全检查点完成对账、撤销旧关系后才可原子接管；旧消息按关系 revision 拒绝。已回收 Agent 不复用身份，创建新个体并显式 handoff。

### 2.3 防止对象混淆

- 以不可复用 `agentInstanceId` 为地址，名称、角色、模型名仅展示，不能作为路由键。
- 复用或扩展版本化信封：`messageId`、认证发送者/接收者实例 ID、源与目标 project/session、任务或 mission 引用、关系 revision、消息类型、`correlationId`、`replyToMessageId`、幂等键；禁止用模型自由文本补齐缺失地址。
- 来源由本地身份绑定；转发记录原始来源与转发链。回复沿经过校验的原请求返回路径，不按“最近对话对象”推断。
- 入队与实际投递前均检查实例、租约/生命周期、项目会话、通信授权、任务范围与 revision；目标未知、已回收、歧义或越界时明确拒绝，不回退至同名对象。
- 不自动分享记忆。附件使用现有显式选择、来源/revision/hash 绑定和接收者作用域检查。

### 2.4 效率与恢复

- 路由由本地目录和规则执行，不调用模型决定收件人。授权边按需解析，不预建 O(|M|×|S|) 信箱或连接；闲置可达边不产生模型请求。
- 接收、投递、已处理、业务完成为不同状态；重复投递复用回执，不重复插入任务。每收件人背压、有限重试、转发跳数和关联链循环检测复用现有机制。
- 不持锁等待模型、用户或网络。忙碌接收者不阻塞其他接收者；反馈单次退避 pn 上限仍为 3 小时，不解释成授权期限或无限重试。
- 关系变更与授权撤销后，在途旧消息不得落入新任务或新个体；恢复从持久化关系与回执对账，不靠重建同名 Agent 猜测路由。

## 4. 测试方案

1. 上层：同项目用 2 个会话主 Agent、2 个具体次级验证默认四对双向可达且无逐边授权弹窗；不同会话只各保留一个沟通主 Agent，不泄露会话历史。跨项目未授权边拒绝，分别验证目标项目主 Agent 批准、用户批准两条路径；源项目主 Agent 自批、冒充目标项目主 Agent、越范围与转授权均拒绝。撤销或到期只影响对应授权边，在途消息复检；另覆盖默认单主多次级。
2. 防混淆：相同名称/模型/角色，不同实例和项目；交错请求、乱序回复、同 messageId 重放、伪造来源、过期关系、目标回收、不同任务复用 correlationId。断言精确目标与任务、无串档。
3. 唯一上级：两个次级并发绑定同一三级只允许一个；两个三级竞争四级同理。非直属上级直发、旧转交句柄、叶子直联兄弟或越级求助均拒绝或经正式代理路由；不得要求叶子模型自行判断对象。
4. 生命周期：投递前撤销、持久化后未投递崩溃、投递后 ack 丢失、旧进程恢复、接管中断、原上级离线。允许可恢复等待，不得双上级、重复业务副作用或错认已完成。
5. 成本与公平：N 个空闲可达 Agent 不产生 N² 初始化/广播调用；叶子提示不含全网目录。用确定性计数和虚拟时钟验证忙碌接收者不饿死其他对象、循环有界、队列可恢复，不设脆弱毫秒性能阈值。
6. 验收执行：使用已有依赖和本地 fake Provider；`npm run check`、coverage 与安全专项、`npm pack`、`verify-package.mjs` 和 `smoke-install.mjs`（按实际脚本参数传入 tarball）。证据记录 commit/dirty、运行 ID、平台、退出码、tarball SHA256 和未满足项。真实服务需另行费用授权，人工体验不由自动断言代签。
7. 跨项目只读：授权后主—主、次级—次级查询/建议可达；直接写文件、改配置/队列、推送 Git、夹带执行命令、用建议自动触发修改均拒绝，在放权模式下也相同。目标项目独立采纳后才按本地权限形成执行任务；来源与优先级不冒充用户。三级/四级同层建议只能由唯一上级代理，不能生成第二指挥关系。

### 7.3 【已由用户澄清解决】首版的策略分歧（我不擅自选定）

| **放行**（宽容） | 兼容存量消息；但"未登记即通过"等于**默认信任**，与卡内"未验证归人工裁决"口径相悖 |
